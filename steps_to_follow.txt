# **Push_swap — Development Roadmap**

Here's the order I'd follow to build the project. The idea is to **finish and test each stage before moving to the next one**. Don't start implementing sorting algorithms before your stack and operations are reliable.

We'll use the decisions we already made:

- **Circular array** for both stacks.
- `head` points to the top element.
- The stack's logical elements are accessed using `(head + i) % cap`.
- Implement the required operations once, then build the sorting algorithms using those operations.

Start here

Create your project structure and decide where each part will live.

### **2. Parse the arguments**

Your program must handle inputs such as:

```
./push_swap 4 67 3 87 23
./push_swap "4 67 3 87 23"
./push_swap 4 "67 3" 87 23
```

Your parsing must:

- Extract all the integers.
- Handle negative numbers.
- Reject non-integer input.
- Detect integer overflow.
- Reject duplicates.
- Handle empty strings and invalid arguments.
- Print `Error\n` to stderr for invalid input.
- Produce no output when there are no arguments.

**Checkpoint:** You should be able to turn valid arguments into a clean array of integers, or reject invalid input.

## **Phase 2 — Stack implementation**

### **3. Create your circular-array stack structure**

We settled on this structure:

```
typedef struct s_stack
{
    int *data;
    int cap;
    int head;
    int size;
}   t_stack;
```

Understand the responsibility of each member:

| Member | Meaning                           |
| ------ | --------------------------------- |
| `data` | The actual allocated array        |
| `cap`  | Physical capacity of the array    |
| `head` | Physical index of the top element |
| `size` | Number of active elements         |

Remember:

```
data[(head + i) % cap]
```

gives you the element at logical position `i`, counting from the top.

**Important:** Use `cap` in the modulo, not `size`. The array's physical boundary is its capacity.

### **4. Implement stack initialization and destruction**

You need functions to:

- Allocate and initialize a stack.
- Set its initial `head` and `size`.
- Free its allocated memory.
- Handle allocation failures properly.

Initially, stack `a` contains all the input values, while stack `b` is empty.

### **5. Implement debugging utilities**

Before implementing operations, make it easy to inspect your stacks.

For example, create a function that prints the logical contents of a stack from top to bottom.

Don't print `data[0]`, `data[1]`, etc. blindly. Remember that the logical top might not be at physical index zero.

**Checkpoint:** Initialize a stack, print its contents, and free it without memory errors.

## **Phase 3 — Implement the 11 operations**

This is one of the most important phases.

Implement every operation independently. Don't put sorting logic inside these functions.

### **6. Swap operations**

- `sa`: Swap the first two elements of stack A.
- `sb`: Swap the first two elements of stack B.
- `ss`: Perform both swaps.

### **7. Push operations**

- `pa`: Push the top element of B onto A.
- `pb`: Push the top element of A onto B.

Remember how we discussed moving elements between circular arrays:

When pushing:

1. Read the source's top value.
2. Advance the source's head.
3. Decrease the source's size.
4. Move the destination's head backward.
5. Write the value at the destination's new head.
6. Increase the destination's size.

This also works when the destination stack is empty.

### **8. Rotate operations**

- `ra`: Move the top element of A to the bottom.
- `rb`: Move the top element of B to the bottom.
- `rr`: Perform both rotations.

For our partially filled circular array, remember that **changing&#x20;**`head`**&#x20;alone is not enough**.

For `ra`, the value at the old top must be copied to the position after the current bottom, then `head` advances.

```
data[(head + size) % cap] = data[head];
head = (head + 1) % cap;
```

### **9. Reverse rotate operations**

- `rra`: Move the bottom element of A to the top.
- `rrb`: Move the bottom element of B to the top.
- `rrr`: Perform both reverse rotations.

Again, because the array may be partially filled, you need to move the bottom value into the newly available position before considering the operation complete.

```
head = (head - 1 + cap) % cap;
data[head] = data[(head + size) % cap];
```

### **10. Test every operation independently**

For each operation, test:

- Empty stack.
- One element.
- Two elements.
- Several elements.
- A partially filled circular array.
- A full circular array.
- A stack whose `head` is not zero.

Also test combinations such as:

```
ra
ra
rra
pb
pa
```

**Checkpoint:** All 11 operations work correctly, including when the circular arrays wrap around.

## **Phase 4 — Operation dispatcher and rank normalization**

### **11. Create an operation dispatcher**

Create one central place responsible for executing operations.

For example, when your sorting algorithm requests `ra`, the dispatcher should:

1. Execute the actual rotation.
2. Print `ra\n` to stdout.
3. Update the operation counters if benchmarking is enabled.

This keeps your sorting algorithms clean.

Your algorithms should decide *which operation to perform*, not manually manipulate the arrays.

### **12. Normalize the values into ranks**

This is an important step before implementing the sorting algorithms.

Instead of sorting the original values, convert them into ranks from `0` to `n - 1`.

Example:

```
Original:  40  -5  100  12
Ranks:      2   0    3   1
```

The smallest value becomes rank `0`, the next smallest becomes rank `1`, and so on.

Why do this?

- You work with a small, predictable range.
- Negative values no longer matter to the sorting algorithms.
- Radix sort becomes straightforward.
- You don't need to repeatedly compare large integer values.

### **13. Implement sortedness and disorder calculation**

You need to know whether the stack is already sorted.

You also need to calculate disorder using inversions.

An inversion is a pair of elements where the earlier element is greater than the later element.

\\[ \text{Disorder} = \frac{\text{Number of inversions}}{n(n-1)/2} \\]

For example:

```
4 67 3 87 23
```

There are 4 inversions out of 10 possible pairs:

\\[ \text{Disorder} = 4/10 = 0.4 \\]

A fully sorted stack has disorder `0`, while a reverse-sorted stack has disorder `1`.

Handle stacks with fewer than two elements separately to avoid division by zero.

**Checkpoint:** You can determine whether a stack is sorted and calculate its disorder correctly.

## **Phase 5 — Implement the sorting strategies**

Now the actual sorting begins.

Implement the strategies independently. Don't mix adaptive selection into them yet.

### **14. Handle tiny inputs first**

Create dedicated sorting functions for:

- 2 elements.
- 3 elements.
- 4 elements.
- 5 elements.

These cases are small enough to handle with carefully chosen operations.

Test every possible permutation for these sizes.

### **15. Implement&#x20;**`--simple`

O(n²)

The simple strategy should use an algorithm with quadratic complexity.

A natural approach is selection-style sorting:

- Find the smallest element.
- Bring it to the top using rotations.
- Push it to stack B.
- Repeat.
- Push the elements back to A.

The important thing is to translate the algorithm into allowed stack operations.

### **16. Implement&#x20;**`--complex`

O(n log n)

Implement radix sort using the normalized ranks.

The binary representation of each rank determines which elements move between A and B.

You'll use:

- `pb`
- `pa`
- `ra`

This is particularly suitable for your rank normalization.

### **17. Implement&#x20;**`--medium`

O(n√n)

Implement a chunk-based strategy.

The general idea:

1. Divide the ranks into chunks.
2. Push elements belonging to the current chunk from A to B.
3. Repeat for the remaining chunks.
4. Bring the largest elements back from B to A in descending order.

You'll need to experiment with chunk sizes and rotations to reduce the number of operations.

### **18. Implement&#x20;**`--adaptive`

Default strategy

Once all three strategies work, implement the adaptive selection.

Using the thresholds we discussed:

| Disorder             | Strategy |
| -------------------- | -------- |
| Less than 0.2        | Simple   |
| 0.2 to less than 0.5 | Medium   |
| 0.5 or greater       | Complex  |

If the user doesn't specify a strategy, use adaptive by default.

## **Phase 6 — Benchmarking**

### **19. Implement&#x20;**`--bench`

This option should report information to **stderr**, without contaminating the operations printed to stdout.

We discussed reporting:

- Disorder.
- Selected strategy.
- Disorder class.
- Total number of operations.
- Count of each operation type.

For example, you should be able to distinguish how many times you used `ra`, `pb`, `rr`, etc.

Make sure benchmarking does not change the actual sorting behavior.

### **20. Tune your algorithms**

Use the performance targets from your subject:

| Input size | Pass         | Good        | Excellent   |
| ---------- | ------------ | ----------- | ----------- |
| 100        | Under 2,000  | Under 1,500 | Under 700   |
| 500        | Under 12,000 | Under 8,000 | Under 5,500 |

Test:

- Already sorted inputs.
- Reverse-sorted inputs.
- Random inputs.
- Inputs with low disorder.
- Inputs around your adaptive thresholds.

## **Phase 7 — Bonus checker**

### **21. Implement&#x20;**`checker`

The bonus checker should:

1. Read the initial stack from arguments.
2. Read operations from stdin.
3. Execute those operations on the stacks.
4. Check whether A is sorted and B is empty.
5. Print `OK` or `KO`.

Invalid input or invalid instructions should produce `Error\n`.

Keep the checker separate from the sorting program, but reuse your parsing, stack, and operation logic where appropriate.

## **Phase 8 — Final validation**

### **22. Test errors and memory management**

Go through:

- Invalid numbers.
- Integer overflow.
- Duplicate numbers.
- Empty strings.
- Invalid flags.
- Allocation failures.
- Empty stacks and edge cases.
- Memory leaks and invalid memory access.

Make sure:

- `make`, `make clean`, `make fclean`, and `make re` work.
- No unnecessary recompilation happens.
